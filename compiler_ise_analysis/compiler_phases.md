## 2. Phase 1: Lexical Analysis (Scanner)

### 2.1 How the Scanner Operates
- **Input Source**: `cli/main.c:206` opens the file specified by the user (`yyin = fopen(input_file, "r")`) and resets the Flex stream buffer using `yyrestart(yyin)` at line 213.
- **Lexical Pattern Engine**: Implemented in `compiler/lexer.l` using deterministic finite automata (DFA) generated by Flex.
- **Token Passing**:
  When a token is matched, Flex populates the semantic value union member `yylval.nd_obj.name` via the macro:
  ```c
  #define COPY_TOKEN() do { if (yyleng >= sizeof(yylval.nd_obj.name)) { \
      fprintf(stderr, "Lexical Error: token exceeds 99 bytes at line %d\n", countn+1); \
      return 257; \
  } strcpy(yylval.nd_obj.name, yytext); } while (0)
  ```
  It then returns the token integer ID to Bison via `RETURN_TOKEN(token)`.

### 2.2 Token Classification in `compiler/lexer.l`
1. **Keywords**: 26 keywords mapped to token IDs (`lexer.l:25-51`):
   - `printf` (`PRINTFF`), `scanf` (`SCANFF`)
   - Types: `int` (`INT`), `float` (`FLOAT`), `double` (`DOUBLE`), `char` (`CHAR`), `void` (`VOID`), `long` (`LONG`), `short` (`SHORT`), `unsigned` (`UNSIGNED`), `signed` (`SIGNED`), `const` (`CONST`)
   - Flow: `return` (`RETURN`), `for` (`FOR`), `while` (`WHILE`), `do` (`DO`), `if` (`IF`), `else` (`ELSE`), `switch` (`SWITCH`), `case` (`CASE`), `default` (`DEFAULT`), `break` (`BREAK`), `continue` (`CONTINUE`)
   - Special: `sizeof` (`SIZEOF`), `true` (`TRUE`), `false` (`FALSE`), `NULL` (`NULL_TOKEN`)
2. **Identifiers**:
   - Pattern: `{alpha}({alpha}|{digit})*` where `alpha` is `[a-zA-Z_]` and `digit` is `[0-9]`.
   - Token ID: `ID` (`lexer.l:56`).
3. **Constants**:
   - Integers: `{digit}+` -> `NUMBER` (`lexer.l:54`).
   - Floating-point: `{digit}+\.{digit}{1,6}` -> `FLOAT_NUM` (`lexer.l:55`).
   - Strings: `\"([^\"\\]|\\.)*\"` -> `STR` (`lexer.l:91`).
   - Characters: `\'([^\'\\]|\\.)\'` -> `CHARACTER` (`lexer.l:92`).
4. **Operators**:
   - Compound: `++`/`--` (`UNARY`), `<=`, `>=`, `==`, `!=`, `+=`, `-=`, `*=`, `/=`, `%=`, `&&`, `||`, `<<`, `>>`.
   - Single-character: `+`, `-`, `*`, `/`, `%`, `&`, `|`, `^`, `~`, `!`.
5. **Preprocessor Directives**:
   - `#include`: `[ \t]*"#include"[ \t]*[<"][^>\r\n\"]+[>"]` -> `INCLUDE` (`lexer.l:52`).
   - `#define`: `[ \t]*"#define"[^\r\n]* { ; }` -> Skipped without token emission (`lexer.l:53`).
6. **Whitespace & Comments**:
   - Spaces and tabs: `[ \t\r]+ { ; }` (ignored).
   - Newlines: `\n { countn++; }` (increments line counter).
   - Single-line comments: `\/\/[^\r\n]* { ; }` (ignored).
   - Multi-line comments: `\/\*([^*]|\*+[^*/])*\*+\/` -> character-by-character scan counting embedded `\n` to maintain line synchronization (`lexer.l:84-88`).
7. **Invalid Character Handling**:
   - Fallback rule `.` at `lexer.l:93`:
     ```c
     . { if (show_tokens && !quiet_mode) printf("TOKEN line %d CHAR %s\n", countn+1, yytext); return *yytext; }
     ```
     Returns the raw character ASCII value. If the character is not valid in the grammar, Bison reports a syntax error.

## 3. Phase 2: Syntax Analysis (Parser)

### 3.1 Parser Architecture & Algorithm
- **File**: `compiler/parser_wrapper.y`
- **Algorithm**: LALR(1) Bottom-Up Shift-Reduce parser generated by Bison.
- **Grammar Scale**:
  - 1042 lines of Yacc/Bison code.
  - 28 token definitions with semantic value associations.
  - 34 nonterminal types typing AST attributes.
- **Bison Conflicts**:
  Regeneration produces **23 shift/reduce** and **13 reduce/reduce** conflicts (documented in `tests/VALIDATION.md:33`). These arise from classic dangling-else ambiguities and compound type specifiers (`long int`, `unsigned int`). Bison defaults to shifting on shift/reduce conflicts, correctly resolving dangling-else to the innermost `if`.

### 3.2 Precedence and Associativity Rules (`parser_wrapper.y:97-110`)
```yacc
%right '=' ADD_ASSIGN SUB_ASSIGN MUL_ASSIGN DIV_ASSIGN MOD_ASSIGN
%right '?' ':'
%left OR
%left AND
%left BITOR
%left BITXOR
%left AMPERSAND
%left EQ NE
%left LT GT LE GE
%left LSHIFT RSHIFT
%left ADD SUBTRACT
%left MULTIPLY DIVIDE MODULO
%right NOT BITNOT UNARY CAST
%left '[' ']' '(' ')'
```
This correctly implements standard C operator hierarchy (e.g., multiplication binds tighter than addition; relational operators bind tighter than logical AND/OR).

### 3.3 Abstract Syntax Tree (AST) Data Structure
- Defined in `parser_wrapper.y:14-18`:
  ```c
  struct node { 
      struct node *left; 
      struct node *right; 
      char *token; 
  };
  ```
- Constructed via `mknode()` (`parser_wrapper.y:993-1001`):
  Allocates a new node and strdups the node label (`token`).
- Tree Structure:
  - Binary tree representation of n-ary syntax trees.
  - Leaves represent terminals (identifiers, constants, operator names).
  - Internal nodes represent structural abstractions (`program`, `statements`, `declaration`, `for`, `if-else`).
- Traversal & Output:
  `print_tree(head)` invokes recursive `print_inorder(tree)` (`parser_wrapper.y:1010-1020`), printing the inorder visit sequence.
  The offline HTML Explorer renders this tree hierarchically using native `<details><summary>` HTML elements (`cli/explorer.h:24-31`).

## 4. Phase 3: Semantic Analysis

Semantic analysis is integrated directly into the syntax-directed translation actions within `compiler/parser_wrapper.y`.

### 4.1 Implemented Semantic Checks

#### A. Variable Declaration Checking (Use-Before-Declaration)
- **Function**: `check_declaration(char *c)` (`parser_wrapper.y:856-874`).
- **Mechanism**:
  1. Checks if the symbol `c` belongs to a hardcoded whitelist of **47 standard library functions** (`printf`, `scanf`, `strlen`, `strcpy`, `malloc`, `free`, `exit`, `sqrt`, `pow`, etc.). If matched, declaration is accepted implicitly.
  2. For all other identifiers, invokes `search(c)` against `symbol_table`.
  3. If not found (`!q`), logs a semantic error:
     ```c
     add_error("Line %d: Variable \"%s\" not declared before use!\n", countn+1, c);
     ```

#### B. Duplicate Declaration Checking
- **Function**: `add_symbol(char c, const char *name)` (`parser_wrapper.y:933-991`).
- **Mechanism**:
  When declaring a variable (`c == 'V'`), checks `q = search((char*)name)`.
  If the variable already exists (`q != 0`), it emits:
  ```c
  add_error("Line %d: Multiple declarations of \"%s\" not allowed!\n", countn+1, name);
  ```

#### C. Keyword Shadowing Prevention
- **Code**: `parser_wrapper.y:937-944` in `add_symbol()`.
- **Mechanism**:
  Compares new variable identifiers against an array of 20 reserved words (`reserved[20]`: `"int"`, `"float"`, `"if"`, `"while"`, `"main"`, `"return"`, etc.).
  If a match is found:
  ```c
  add_error("Line %d: Variable name \"%s\" is a reserved keyword!\n", countn+1, name);
  ```

#### D. Type Compatibility and Implicit Conversion
- **Function**: `check_types(char *type1, char *type2)` (`parser_wrapper.y:891-917`).
- **Conversion Codes**:
  - `0`: Identical types (no conversion needed).
  - `1`: `int` assigned `float` (truncation / `floattoint`).
  - `2`: `float` assigned `int` (promotion / `inttofloat`).
  - `3`: `int` assigned `char` (`chartoint`).
  - `4`: `char` assigned `int` (`inttochar`).
  - `5`: `float` assigned `char` (`chartofloat`).
  - `6`: `char` assigned `float` (`floattochar`).
- **AST Node Injection**:
  In `declarator` (`parser_wrapper.y:306-340`), if a type conversion is detected, an explicit conversion node (`"floattoint"`, `"inttofloat"`, etc.) is injected into the AST between the variable and the expression.
  In `binary_expression` (`parser_wrapper.y:682-720`), mixed operands cause the lower-precision operand to be wrapped in a conversion node and the result type promoted to the higher type.

#### E. Constant Divide-by-Zero Checking
- **Code**: `parser_wrapper.y:727-729` in `binary_expression()`.
- **Mechanism**:
  If both operands can be evaluated at compile time (`can_eval()`) and the operator is `/` or `%` with divisor `b == 0`:
  ```c
  add_error("Line %d: Constant division or modulo by zero!\n", countn+1);
  ```

### 4.2 Missing / Unimplemented Semantic Checks
1. **Block Scoping**: The symbol table is flat; variables declared in inner `{ ... }` blocks shadow globally and cause false redeclaration errors.
2. **Function Parameter Type & Arity Checking**: Function definitions and calls are parsed, but the compiler does not verify that the number and types of arguments in a call match the function's declaration.
3. **Array Bounds Checking**: Compile-time constant array accesses (e.g., `arr[15]` for `arr[10]`) are not verified against declared array dimensions.
4. **Contextual Flow Constraints**: `break` and `continue` statements are accepted inside any block, even outside loops or switches.

## 5. Supporting Component: Symbol Table Management

### 5.1 Data Structure & Memory Layout
Defined in `parser_wrapper.y:52-58`:
```c
struct dataType {
    char * id_name;     // Identifier name (e.g., "x", "sum", "printf")
    char * data_type;   // Data type string ("int", "float", "char", "void", "CONST")
    char * type;        // Entry category ("Variable", "Constant", "Header", "Function", "Keyword")
    int line_no;        // 0-indexed line number where first declared
    char * value;       // Compile-time string representation of estimated value
} symbol_table[300];

int count = 0;          // Number of active entries (capacity: 300)
```

### 5.2 Key Operations
1. **Insertion (`add_symbol(char c, const char *name)`)**:
   - `c == 'H'`: Header inclusion (`#include <stdio.h>`), category `"Header"`.
   - `c == 'V'`: Variable declaration (`int x`), category `"Variable"`, initial value `"NULL"`.
   - `c == 'C'`: Numeric or character literal (`10`, `5.5`), category `"Constant"`, data type `"CONST"`, value equal to literal.
   - `c == 'F'`: Function declaration or definition (`int main()`), category `"Function"`.
   - Capacity check: If `count >= 300`, logs error and stops insertion (`parser_wrapper.y:934`).
2. **Lookup (`search(char *type)`)**:
   - Scans linearly in reverse order from `count - 1` down to `0`.
   - Returns `-1` if found, `0` if not found.
3. **Type Retrieval (`get_type(char *var)`)**:
   - Scans from `0` to `count - 1` matching `id_name`.
   - Returns `data_type` if found, or `"unknown"` if undeclared.
4. **Value Management (`set_symbol_value()`, `get_symbol_value()`)**:
   - Used for constant propagation and explorer display.
   - Updates the `value` field with `strdup(val)` upon assignment.

### 5.3 Symbol Lifecycle Walkthrough
Trace of `int a = 10;` from `examples/arithmetic.c`:
1. Lexer encounters `int`: Sets global string `type = "int"`.
2. Lexer encounters `a`: Bison parses `direct_declarator: ID`.
   - Calls `add_symbol('V', "a")`.
   - `search("a")` returns `0`.
   - `symbol_table[1]` initialized: `id_name = "a"`, `data_type = "int"`, `type = "Variable"`, `line_no = 6`, `value = "NULL"`.
3. Lexer encounters `= 10`: Bison parses `value: NUMBER`.
   - Calls `add_symbol('C', "10")`.
   - `symbol_table[2]` initialized: `id_name = "10"`, `data_type = "CONST"`, `type = "Constant"`, `value = "10"`.
4. Bison reduces `declarator`:
   - Calls `set_symbol_value("a", "10")`.
   - Updates `symbol_table[1].value` to `"10"`.
   - Emits TAC: `a = 10`.

## 6. Phase 4: Intermediate Code Generation (IR)

### 6.1 IR Architecture & Representation
- **Representation**: Three-Address Code (TAC), stored as a sequence of formatted null-terminated strings in:
  ```c
  char icg[500][512];
  int ic_idx = 0;       // Capacity: 500 instructions
  ```
- **Emission Function**: `emit_ir(const char *format, ...)` (`parser_wrapper.y:672-680`) verifies buffer capacity and formats instructions via `vsnprintf`.

### 6.2 Instruction Set & Translation Patterns

#### A. Assignments & Initializations
- Declaration without value: `emit_ir("%s = NULL\n", var)` -> `x = NULL`
- Direct assignment: `emit_ir("%s = %s\n", lhs, rhs)` -> `x = 5`
- Array assignment: `emit_ir("%s[%s] = %s\n", arr, idx, val)` -> `arr[i] = 10`
- Pointer dereference: `emit_ir("*%s = %s\n", ptr, val)` -> `*ptr = 20`

#### B. Arithmetic & Expressions
- Synthesizes temporaries (`t0`, `t1`, `t2`, ...) via `temp_var++`:
  `emit_ir("%s = %s %s %s\n", temp, left, op, right)` -> `t0 = a + b`
- Unary operators:
  `t1 = - x`, `t2 = ! x`, `t3 = ~ x`
- Function calls:
  `emit_ir("%s = call %s\n", temp, func)` -> `t0 = call printf`

#### C. Control Flow Translation
- **If-Else (`parser_wrapper.y:209-213`)**:
  Synthesizes labels `L0`, `L1` using `label++`.
  Emits:
  ```
  if (a < b) GOTO L0 else GOTO L1
  LABEL L0:
    [then-block instructions]
  LABEL L1:
    [else-block instructions]
  GOTO next
  ```
- **While Loop (`parser_wrapper.y:201-205`)**:
  ```
  if (i < 10) GOTO L0 else GOTO L1
  LABEL L0:
    [loop body]
  JUMP to L0
  LABEL L1:
  ```
- **For Loop (`parser_wrapper.y:197-200`)**:
  ```
  LABEL L0:
  if NOT (i < 10) GOTO L1
  [body]
  JUMP to for_loop
  ```

## 7. Phase 5: Code Optimization

### 7.1 What is Implemented
The compiler contains an active, compile-time **Constant Folding** and **Constant Propagation** subsystem located in `binary_expression()` (`parser_wrapper.y:682-755`).

#### Mechanism:
1. When reducing an expression, `can_eval(operand)` (`parser_wrapper.y:656-662`) checks if the operand is a numeric literal or an identifier with a known constant value in `symbol_table`.
2. If both operands can be evaluated:
   - `get_num_val()` extracts values as doubles.
   - If operands are integers, it performs compile-time 32-bit integer arithmetic (`+`, `-`, `*`, `/`, `%`, `&`, `|`, `^`, `<<`, `>>`).
   - Checks for overflow (`INT_MIN` to `INT_MAX`) and divide-by-zero.
   - If valid, writes the pre-computed numerical string directly into `result.name` (e.g., `"14"` instead of allocating temporary `"t0"`).
3. Unary operators (`-`, `!`, `~`, casts, ternary `?:`) similarly fold constant operands directly at compile time (`parser_wrapper.y:375, 393, 404, 414, 438`).

### 7.2 Implementation Quirk / Codebase Artifact
Because `binary_expression` folds the constant into `result.name` before calling `emit_ir`:
```c
if (!folded) snprintf(result.name, sizeof(result.name), "t%d", temp_var++);
emit_ir("%s = %s %s %s\n", result.name, left.name, op, right.name);
```
When folding succeeds (e.g., for `a = 10, b = 20; sum = a + b`), `result.name` contains `"30"`. The IR emission then prints:
```
30 = a + b
sum = 30
```
This is a notable implementation quirk in the existing codebase: constant folding optimizes the downstream value, but the emitted IR line retains the computed literal on the left-hand side instead of omitting the redundant instruction.

### 7.3 What is NOT Implemented
- **Common Subexpression Elimination (CSE)**: Redundant identical expressions are recomputed.
- **Dead Code Elimination**: Unused variables and unreachable code after `return` are not stripped.
- **Loop Invariant Code Motion**: Invariant expressions are not hoisted out of loops.
- **Peephole Optimization**: Consecutive redundant jumps (`GOTO L1; LABEL L1:`) are not collapsed.

## 8. Target Code Generation & Runtime Execution

### 8.1 Architectural Division: Frontend vs Backend
In standard compiler design, the backend generates target assembly or machine instructions.
In this project:
- **`ccompiler` Frontend**: Translates C source code into Tokens -> Parse Tree -> Symbol Table -> 3-Address Code IR.
- **Execution Backend**: The project does NOT implement a custom machine code assembler or register allocator. Instead, target compilation is orchestrated via host toolchain delegation (`cli/main.c:158-195`).

### 8.2 Execution Workflow (`-r` / `--run` or `-b` / `--build`)
1. Frontend performs all analysis phases (Lexical, Syntax, Semantic, IR).
2. If any syntax error or semantic error occurred, compilation stops immediately with exit code `1`.
3. If frontend analysis succeeded:
   - `find_c_backend()` searches system paths for an installed `gcc` or `clang` (supports Linux, macOS, MinGW-w64, MSYS2, and w64devkit).
   - `run_backend_compiler()` invokes:
     ```bash
     gcc -o <target_bin> <input_file.c>
     ```
   - If `-r` was passed, `run_binary()` executes `<target_bin>` as a child process and reports its exit code.

## 9. Error Handling and Diagnostics Architecture

The compiler implements a multi-tier diagnostic architecture:

```
[Source Code]
      │
      ├─► Lexical Layer: Macro COPY_TOKEN() checks yyleng >= 100 bytes.
      │     └─► Error: "Lexical Error: token exceeds 99 bytes at line X" -> exits.
      │
      ├─► Syntax Layer: yyerror() called by Bison on ungrammatical tokens.
      │     └─► Error: "Syntax Error: syntax error at line X" -> sets parse_result = 1.
      │
      ├─► Semantic Layer: add_error() records violations in errors[100][100].
      │     ├─► Undeclared variables
      │     ├─► Duplicate declarations
      │     ├─► Reserved keyword collisions
      │     └─► Constant divide-by-zero
      │     └─► Non-fatal during parsing; prints full diagnostic report before exit(1).
      │
      └─► Capacity Guards: Emits errors if Symbol Table (300) or IR (500) overflows.
```
